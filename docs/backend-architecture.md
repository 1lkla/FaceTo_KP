# FaceTo KP · 岗位定向刷题 — 后端架构设计

> 对应画布：《岗位定向刷题 - FaceTo KP》「后端架构设计」页面
> 目标：模块化、可水平扩展，支撑大客户量；核心刷题链路永不受 AI / 爬虫等不稳定依赖拖垮。

## 0. 设计总纲

大客户量下真正的瓶颈不是业务 CRUD，而是两条链路：

1. **LLM 调用**（JD 解析、面经转题、作答点评、模拟面试）——慢（秒级）、贵、外部依赖不可靠；
2. **面经检索**（ES 全文 + 高频考点聚合）——读放大明显。

因此架构的三个第一性决策：

- **业务服务无状态化** → 任意水平扩容；
- **AI 任务全异步化** → 队列削峰、故障隔离；
- **读写路径分离** → 读走三级缓存，写走队列合并落库。

## 1. 分层架构

| 层 | 组成 | 关键职责 |
|---|---|---|
| 客户端层 | Web / 移动 App / 小程序 | Web 为主战场；小程序做引流与面经轻阅读 |
| 接入层 | CDN+WAF · 云 LB · API 网关（APISIX） | JWT 鉴权、限流熔断、灰度路由；**SSE 长连接独立分组** |
| 微服务层 | 7 个域服务（见下） | 按业务域拆分、无状态、独立扩缩容 |
| 异步任务层 | Kafka + 4 类 Worker | 削峰填谷、重试/死信、AI 与爬虫故障隔离 |
| 数据层 | PG / Redis / ES / 向量库 / 对象存储 | 多引擎按需选型，预留分片 |
| 基础设施 | K8s+HPA · Prometheus/Grafana · ELK+OTel · CI/CD | 弹性伸缩与全链路可观测 |

## 2. 微服务模块拆分（对应产品五屏）

| 服务 | 支撑界面 | 职责 | 扩缩特征 |
|---|---|---|---|
| 用户服务 | 全局 | 注册登录、RBAC、会员、多岗位管理 | 低 QPS，常态 2 副本 |
| 岗位服务 | S1 导入 / S2 岗位画像 | JD 管理（文本/链接/截图 OCR 入口）、考点权重存储、画像聚合 | 写少读多，缓存友好 |
| 题库服务 | S3 计划 / S4 详情 | 题目与模块管理、考点标注、版本化 | **强读热点**：CDN + Redis 可挡 90% |
| 刷题服务 | S3 / S4 | 作答记录、进度、AI 点评编排（异步） | 高频小写 → Kafka 合并落库 |
| 面经服务 | S3 面经栏 / S4 溯源 | ES 全文检索、高频考点聚合、订阅推送 | 检索读放大，独立域可摘除 |
| 模拟面试服务 | S5 | 多轮对话编排、SSE 流式输出、实时考点评估 | 长连接 + LLM 直连，单独容量规划 |
| 画像评估服务 | S2 / S5 回流 | 掌握度计算、匹配度、弱项分析回流 | 事件驱动，消费 Kafka |

## 3. 异步任务层（稳定性核心）

**Kafka topics：** `jd.parse`（JD 解析）、`answer.grade`（作答点评）、`crawler.push`（面经采集）、`notify.send`（通知）。

- **AI Worker 池**：JD 考点提取、面经转题、作答点评。LLM 并发用**令牌桶**控制；主模型失败**降级到备用模型**；全程指标上报（延迟、成功率、token 成本）。
- **面经爬虫 Worker**：定时采集、去重清洗、入 ES；频率受控，故障不影响主站。
- **OCR Worker**：JD 截图转文本，GPU 池化，异步回写岗位服务。
- **通知 Worker**：计划提醒、面经订阅推送，批量削峰发送。

**为什么 AI 必须全异步**：同步链路挂 LLM 等于把网关超时、连接池、用户耐心全绑在一个不可控外部依赖上。异步化后，峰值只是排队时间变长，系统不崩。

## 4. 数据层选型与预留

| 存储 | 用途 | 扩容预案 |
|---|---|---|
| PostgreSQL | 业务主库（用户/岗位/题目/作答） | 主从读写分离；核心表预留 `user_id` 分片键，需要时迁分库分表或 TiDB |
| Redis 集群 | 热点缓存、会话、分布式限流、排行榜 | 缓存防击穿 singleflight + 逻辑过期；Cluster 水平扩 |
| Elasticsearch | 面经全文检索、考点聚合 | 按季度 rollover 索引，冷热分层 |
| 向量库 | JD↔考点↔面经语义匹配 | 量小用 pgvector 复用 PG；量大迁 Milvus，接口提前抽象 |
| 对象存储 COS | JD 截图、面试录音、导出报告 | 天然无限，走 CDN 回源 |

## 5. 大客户量扛压六决策（画布已图示）

1. **无状态服务**：状态全在 Redis/DB，Pod 可杀可扩，HPA 按 QPS 秒级扩缩。
2. **AI 全异步**：LLM 调用只进队列不扛请求；令牌桶 + 多模型降级，LLM 故障不拖垮主站。
3. **读三级缓存**：CDN → Redis → DB，读多写少场景 90% 流量到不了数据库。
4. **写合并落库**：作答/进度先进 Kafka，Worker 批量聚合写 PG，写容量高一个量级。
5. **SSE 长连接隔离**：模拟面试在网关单独分组，独立超时与连接数上限。
6. **分片预留 + 熔断降级**：跨服务调用一律超时 + 熔断；面经/爬虫域可整体摘除，核心刷题链路永不受牵连。

## 6. 落地顺序建议

1. **MVP（单体起步）**：FastAPI 单体 + PG + Redis + 一个 Kafka + AI Worker——模块化按包边界预留（`domains/user|job|question|practice|exp|interview|profile`），不急着拆服务；
2. **量起后**：先拆模拟面试服务（长连接/LLM 特征最明显），再拆面经检索（读放大），其余按域逐步剥离；
3. **大客户前**：完成分片键预留迁移演练、LLM 多模型降级演练、全链路压测（重点：作答写入合并与 SSE 并发）。

> 原则：**按域拆包的模块化单体起步，按负载特征拆服务的微服务演进**——既不一上来过度设计，也不给扩容埋单体炸弹。
